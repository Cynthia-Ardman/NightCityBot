BUG 1 — NameError: name 'RentResult' is not defined [HIGH]
File: economy.py line 1596 Class defined: RentRunResult (line 39) Code references: RentResult (line 1596) — does not exist

What it does: This is the concurrent rent collection guard. When a second rent run is attempted while one is already in progress, the code tries to return RentResult() to gracefully exit. Since RentResult is not defined anywhere in the file (only RentRunResult exists), this throws a NameError.

How to trigger: Admin A runs !collect_rent on a large guild (takes minutes). Admin B runs !collect_rent while it's still going, or the auto-scheduler fires during a manual run.

Impact: Instead of the intended "⚠️ A rent collection is already in progress. Please wait." message, the user gets a generic error from the error handler. The guard effectively doesn't work — the NameError is raised before the return, so the function crashes, the rent_lock is never acquired by the second caller, and the lock is not re-entered (the first caller still holds it). So concurrent runs are still prevented by the lock, but the feedback is broken and the crash logs noise.

Fix: Change RentResult() to RentRunResult(charged=0, skipped=0, errors=0).

BUG 2 — PriceSelectView hangs 60 seconds on cancel or invalid input [MEDIUM]
File: inline_helpers.py lines 80 and 86

What it does: When a user picks "Custom amount..." from the price dropdown, the view awaits collect_text_input. If the user types cancel (returns None, line 80) or a non-numeric value (raises ValueError, caught at line 84, followup sent at line 85), the callback returns without calling self.stop(). The only self.stop() is at line 92, which is only reached on the success path.

How to trigger: Any sell/trade flow that uses PriceSelectView. User picks "Custom amount...", then either:

Types cancel
Types something non-numeric like "five thousand"
Waits 60s for the text input to time out
Impact: The caller's await price_view.wait() blocks for the full view timeout (60 seconds) even though the user has already abandoned the input. During this time, the entire sell/trade flow is frozen. The user and the other party see no feedback. After 60s, price_view.result is None and the caller continues, typically exiting since there's no price.

Fix: Add self.stop() before both return statements:

if text is None:
    self.stop()  # <-- add
    return
try:
    self.result = int(text.replace(",", "").replace("$", ""))
except ValueError:
    await interaction.followup.send("❌ Invalid price.", ephemeral=True)
    self.stop()  # <-- add
    return

BUG 5 — Fixer Add Item continue_btn: async DB call before interaction response [LOW-MEDIUM]
File: fixer_hub.py line 971

What happens: When a Fixer clicks "Continue →" on the Add Item picker, ensure_character_active() (an async DB query) runs at line 971 before the interaction is deferred at line 977. Discord requires a response within 3 seconds. If the DB query takes longer (pool contention, slow query, network latency), the interaction silently fails with "This interaction failed" shown to the user.

How to trigger: Fixer clicks Continue while the DB pool is busy (e.g., during a rent collection run that's holding many connections). The ensure_character_active query waits for a pool connection, exceeding the 3s Discord deadline.

Impact: The user sees "This interaction failed." No data is corrupted — the flow simply never starts. Annoying but not dangerous.

Fix: Move await interaction.response.defer(ephemeral=True) to line 965 (before any validation), then change the error responses at lines 966, 969, 972 from interaction.response.send_message to interaction.followup.send.

Note: The player_select callback (line 909-925) has the same pattern — _resolve_user_select (potentially async fetch_member) + get_active_characters before the first response. However, _resolve_user_select usually hits the member cache (fast path), so this is lower risk.

BUG 6 — Rent run sentinel recorded before any member is processed [LOW]
File: economy.py line 1655

What happens: rent_run_record is called at line 1655, before the member processing loop starts at line 1662+. If the bot crashes immediately after writing the sentinel (OOM, network outage, hosting restart), subsequent !collect_rent calls (without -force) see "Rent already collected this month" even though zero members were charged.

How to trigger: Admin runs !collect_rent. Sentinel writes successfully. Bot crashes before processing any members (e.g., Replit restarts the container).

Impact: Admin must know to use !collect_rent -force to override. The auto-rent scheduler uses a separate sentinel and is not affected. Low real-world risk since the admin gets the "already collected" message and can force it.

Fix: Move rent_run_record to after the processing loop completes (near line 1885). Or accept the current behavior since -force exists.
