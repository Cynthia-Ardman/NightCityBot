# Bug Audit Prompt

Paste this into a Replit Agent chat to find the recurring bug categories.

---

You are auditing NightCityBot for bugs. DO NOT fix anything — only report what you find. Output a numbered bug list with file, line range, severity (critical/high/medium/low), and a one-sentence description.

Search for these 6 specific bug categories across all files in `NightCityBot/cogs/` and `NightCityBot/utils/`. Examine every file — do not skip any.

---

## Category 1: Dead References (classes, functions, or variables that were deleted but are still referenced elsewhere)

Grep the full codebase for every class name and function name defined in any cog or util file. For each one, confirm every reference to it across the project resolves to something that exists. Pay special attention to:
- View and Modal class names used in isinstance checks, constructor calls, or type annotations
- Imports that reference classes/functions no longer defined in the source module
- String references to removed `!command` names in help text, error messages, docstrings, and embed content (e.g. `!my_inventory`, `!trade`, `!inv_give`, `!admin_shop`, `!wh_sell`, `!cw_sell`, `!cw_buy`)

Also check the reverse: every `import` statement in every file — does the imported name actually exist in the source module?

---

## Category 2: View Lifecycle Bugs (parent views interfering with child views)

All interactive hubs use a pattern where a top-level View (e.g. `FixerTopView`, `PlayerHubView`) transitions to sub-views by calling `interaction.response.edit_message(view=new_view)`. Audit every such transition for these issues:

a) **Zombie parent timeout**: When a parent view transitions to a child view, does the parent call `self.stop()` BEFORE the edit? If not, the parent's `on_timeout` will fire later and call `message.edit(view=None)`, destroying the child view's buttons. Check every `on_timeout` in every View class and trace what it does.

b) **delete_after conflicts**: If the hub command sends with `delete_after=120`, the message will auto-delete 120 seconds after SEND, not after last interaction. If a user spends more than 2 minutes navigating, the message vanishes mid-flow. Check all hub command functions for `delete_after` on the initial send and verify the timeout is appropriate for multi-step flows.

c) **Back button staleness**: When a sub-view has a "Back" button that returns to the parent, does it create a FRESH parent view instance, or does it reuse the old (now stopped) instance? Reusing a stopped view means its timeout will never fire and it becomes a zombie.

d) **edit_message vs send_message**: After adding components to a view dynamically (e.g. a character select dropdown), does the callback use `edit_message(view=self)` to re-render, or `send_message` which creates a new message and leaves the old one stale? Check every `add_item()` call followed by a response.

---

## Category 3: Financial Sign Errors (wrong debit/credit direction or wrong account)

The bot uses the UnbelievaBoat API via `NightCityBot/services/unbelievaboat.py`. Balance changes are dicts like `{"cash": amount, "bank": amount}` where negative = debit.

Audit every call to `update_balance` or `edit_balance` (or any function that wraps them) across all cog files. For each one, verify:

a) **Refund paths use `{"bank": -price}` not `{"cash": -price}`**: Refunds that use cash can push the recipient's cash balance negative. Every refund/rollback path should debit from bank. Search for all error/except/rollback branches in sale, trade, and install flows.

b) **Debit/credit direction is correct**: In a sale: buyer gets debited (negative), seller gets credited (positive). Check every two-sided transaction to confirm the signs aren't flipped.

c) **Cash/bank split uses `max(cash, 0)` before splitting**: When debiting, the pattern should be `cash_deduct = min(cost, safe_cash)` then `bank_deduct = cost - cash_deduct`. Verify `safe_cash` is `max(cash_balance, 0)` to prevent negative cash from amplifying the bank deduction.

d) **Double-debit on rollback failure**: If a sale debits the buyer, then the credit to the seller fails, the code should refund the buyer. But if the refund ALSO fails, the buyer is now out the money with no recourse. Check that these paths log a critical error and create a `pending_transfers` record for admin intervention.

---

## Category 4: Missing `interaction_check` on Views with Accept/Decline Buttons

Any View that sends a DM or ephemeral message to a specific user with action buttons (Accept, Decline, Confirm, etc.) MUST have an `interaction_check` that verifies `interaction.user.id == self.expected_user_id`. Without it, any user who somehow accesses the message can click the buttons.

Check every View class that has buttons meant for a specific recipient. These include:
- Trade confirmation views (DM to buyer)
- Store buy confirmation views (DM to store owner)
- Approval views (sent to specific approver channels)
- Any view created with a specific `user_id` or `recipient_id` parameter

For each one, confirm `interaction_check` exists and checks the correct ID.

---

## Category 5: Concurrency / Race Conditions in Multi-Step Flows

Hub flows often span multiple interactions (select user → select item → enter details → confirm). Between any two steps, another user (or the same user in a different tab) could modify the underlying data.

Check for:

a) **Stale item reference**: After a user selects an item from a dropdown, does the code re-fetch the item from the database before executing the action? Or does it use cached data from the dropdown population step? If the item was sold/transferred between selection and execution, the operation should fail gracefully.

b) **Missing re-verify before financial operations**: Before debiting a buyer, does the code confirm the seller still owns the item? Look for `pi_get_item` or equivalent checks immediately before `update_balance` calls.

c) **Inventory mutations outside locks**: The `ResourceLockManager` provides per-key locks. Verify that operations which read-then-write inventory (check stock → debit buyer → remove item → credit seller) hold a lock for the entire sequence. Look for cases where the lock is acquired for only part of the sequence.

d) **`collect_text_input` timeout gaps**: After `collect_text_input` returns a value and before the bot acts on it, is there a window where another interaction could invalidate the input? This matters especially for item UUIDs and prices entered via text.

---

## Category 6: Stale Docstrings, Help Text, and Command References

Search all Python files (including test files) for:
- References to command names that no longer exist as `@commands.command` or `@commands.hybrid_command` definitions (e.g. `!my_inventory`, `!trade`, `!inv_give`, `!inv_add`, `!inv_remove`, `!inv_reassign`, `!wh_buy`, `!wh_sell`, `!wh_list`, `!store_inv`)
- Docstrings that describe behavior no longer matching the code (e.g. claiming a modal is used when the flow now uses inline collection)
- Help embed text that references removed buttons, removed flows, or old UX patterns
- Test assertions that check for removed modal class names or send_modal calls
- Comments referencing "Task #N" that describe work already completed — these aren't bugs but flag them separately as cleanup opportunities

---

## Category 7: Write End-to-End Flow Tests

The current test suite tests individual button callbacks in isolation (e.g. "click Trade → assert TradeSetupView is sent"). But no tests simulate a full multi-step flow where one interaction's output feeds into the next. This is the gap where most of the recurring bugs live — view lifecycle issues, stale data between steps, dynamic component rendering failures.

Write a new test file `NightCityBot/tests/test_e2e_flows.py` that chains multiple interaction steps together. Use the existing test helpers as a base (the patterns in `test_fixer_hub.py` and `test_player_hub.py`). Each test should:

1. Create the cog and invoke the hub command
2. Find and click a button on the returned View
3. Capture the View sent in the response
4. Find and interact with a component on THAT View (select a user, select an item, etc.)
5. Continue through to the final step (confirm, cancel, or error)
6. Assert the expected outcome at EACH intermediate step, not just the final one

### Required flows to test (one test per flow minimum):

**Flow A — Fixer: Top → Player → Add Item → select user → select character → enter text → verify item created**
This is the flow where the `PlayerAddItemPickerView` had a bug where the character dropdown was never rendered because the callback used `send_message` instead of `edit_message`. The test should:
- Click "Player" on `FixerTopView` → assert `PlayerSubView` is returned and parent is stopped
- Click "Add Item" on `PlayerSubView` → assert `PlayerAddItemPickerView` is returned
- Simulate `UserSelect` callback with a mock member → assert the view was re-rendered with a character dropdown present (`edit_message(view=self)` was called)
- Simulate character dropdown selection → assert `selected_character` is set
- Click "Continue" → assert `collect_text_input` is called and `pi_add_item` is invoked with correct args

**Flow B — Fixer: Top → Player → Back → Player (view lifecycle)**
This tests the zombie parent timeout and back button staleness bugs:
- Click "Player" on `FixerTopView` → capture the returned `PlayerSubView`
- Assert `FixerTopView.stop()` was called (parent is no longer ticking)
- Click "← Back" on `PlayerSubView` → assert a FRESH `FixerTopView` is created (not the old instance)
- Assert the new `FixerTopView` has `message` set correctly
- Click "Player" again → assert it still works (not a stale/stopped view)

**Flow C — Player Hub: Trade Item → select buyer → select item → select buyer character → Continue → price → DM confirm → accept**
This is the full trade flow:
- Click "Trade Item" on `PlayerHubView` → assert `TradeSetupView` returned
- Simulate `UserSelect` with a buyer who has active characters → assert character dropdown appears
- Simulate character dropdown selection → assert `selected_buyer_char_name` set
- Simulate item dropdown selection → assert `selected_group_idx` set
- Click "Continue →" → assert `collect_text_input` is called for price
- Mock price response → assert `TradeConfirmView` is sent via DM to the buyer
- Simulate buyer clicking "Accept" → assert `pi_update_owner` and `update_balance` called with correct args and signs
- Assert audit log (`ih_record_event`) was called

**Flow D — Player Hub: Trade Item → self-trade blocked**
- Set buyer = seller (same user ID) in `TradeSetupView`
- Click "Continue →" → assert the self-trade error message is returned
- Assert NO financial operations were attempted

**Flow E — Player Hub: Trade Item → stale item (sold between selection and confirmation)**
- Start a trade flow normally through Continue → price entry
- Mock `pi_get_item` to return `None` (item was sold by another flow between steps)
- Assert the trade is blocked with an appropriate error, and no money moves

**Flow F — Ripperdoc Hub: Sell → select patient → select stock item → enter price → DM confirm → accept**
- Open `RipperdocMenuView` → click "Sell"
- Simulate `SellSetupView` user select and item select
- Click Continue → enter price
- Assert DM sent to patient with `DMConfirmView`
- Simulate accept → verify `pi_add_item` called BEFORE stock removal, balance operations correct

**Flow G — Gunstore Hub: Sell restricted gun → approval flow**
- Sell a restricted gun → assert the gun-approvals channel embed is posted
- Simulate Fixer approval reaction
- Assert buyer DM sent with `GunDMConfirmView`
- Simulate buyer accept → verify full financial chain

**Flow H — Admin Panel: Add Item to player (inline text flow)**
- Open `AdminShopMenuView` → click "Add Item"
- Simulate `UserSelect` → character dropdown appears
- Select character, click Continue
- Mock `collect_text_input` → verify `pi_add_item` called with correct owner, character, item details

### Test infrastructure guidance:

Use `asyncio.run` / `_run()` pattern already in the codebase. Helper functions already available: `_make_bot()`, `_make_interaction()`, `_make_member()`, `_find_button()`, `_find_user_select()`.

For `collect_text_input` mocking, patch `NightCityBot.cogs.<module>.collect_text_input` as `AsyncMock(return_value="<input text>")`.

For database calls, patch `pi_add_item`, `pi_get_item`, `pi_get_by_owner`, `pi_update_owner`, `ih_record_event`, `get_active_characters` at the module level where they're imported.

For UnbelievaBoat balance operations, mock `cog.unbelievaboat.get_balance` and `cog.unbelievaboat.update_balance`.

Key assertions at each step:
- Was `self.stop()` called on the outgoing view?
- Was `edit_message` called (not `send_message`) for view transitions on the same message?
- Was `interaction.response.defer` called before any awaited work?
- Do the args passed to `pi_add_item` / `update_balance` have the correct signs, correct user IDs, correct character names?

After writing the tests, run them with `python -m pytest NightCityBot/tests/test_e2e_flows.py -v` and fix any failures in the TESTS (not the production code — if a test reveals a real bug, note it in a comment but keep the test as a failing reminder).
